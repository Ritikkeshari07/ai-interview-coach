# AI Interview Coach — Project Report

## 1. Title, abstract, and problem
**AI Interview Coach** is an AI-powered web application that simulates technical and HR interviews. It addresses the lack of scalable personalised practice by asking focused questions, evaluating answers objectively, and presenting an improvement plan.

## 2. Objectives and target users
The goal is to help B.Tech students, college students, freshers and job seekers build interview confidence. Users can practise DSA, programming, DBMS, OS, networks, OOP and general technical skills at three difficulty levels.

## 3. Application overview and features
The platform has landing, setup, live interview, results, dashboard and learning pages. It supports role and custom-instruction inputs, timer/progress UI, skip/end controls, score out of ten, strengths, weaknesses, missing points, suggestions, model answers, question reports and local interview history.

## 4. Technology stack and LLM
Frontend: React, Vite, CSS, React Router and Lucide. Backend: Node.js/Express with Zod, Helmet, CORS and rate limiting. AI: server-side calls to NVIDIA's hosted NIM API using the OpenAI-compatible Chat Completions endpoint, running `nvidia/nemotron-3.5-lightning-30b-a3b`, a reasoning-capable Mixture-of-Experts model (`AI_PROVIDER=nvidia`). An alternate OpenAI Responses API path, and a simpler non-reasoning `meta/llama-3.2-3b-instruct` NVIDIA model, are also supported behind the same `AI_PROVIDER`/`NVIDIA_MODEL` switches. Docker builds the frontend and serves it from Express.

## 5. Vibe Coding methodology and phases
The project was iteratively planned, implemented in modules, tested at build/API level, and repaired after defects were found. Phases: planning; UI; client routes; Express API; prompt modules; NVIDIA NIM (Nemotron 3.5 Lightning) integration; streaming; resilience (retries, JSON repair, deterministic skip-handling); security; Docker/AWS deployment; live verification.

## 6. Prompt engineering strategy and sample prompts
Separate modules prevent one giant prompt. Question generation asks for one non-repeated question tailored to subject/difficulty. Evaluation requires JSON fields `score`, `verdict`, strengths, weaknesses, missing points, suggestions, ideal answer and follow-up. HR assessment prioritises communication/professionalism; technical assessment includes correctness, depth, complexity and edge cases. Final reporting aggregates all results. The learning assistant requires simple and detailed explanations, examples, pitfalls, and a related question.

## 7. Architecture and data flow
Browser → Express `/api/interview/start` → NVIDIA NIM (nemotron-3.5-lightning-30b-a3b) for question. Browser sends question/answer → Express validates and, if the answer is non-empty, asks the model for a JSON evaluation (empty/skipped answers are scored deterministically at score 0 without an API call); browser displays score and feedback. Completion → final report → browser localStorage. The learning assistant route forwards model text deltas through SSE to a Fetch stream reader.

## 8. Streaming implementation
The backend calls the NVIDIA NIM Chat Completions endpoint with `stream: true` (OpenAI-compatible SDK), reads `delta.content` chunks and forwards each as an SSE `token` event. The client reads chunks directly with `ReadableStream.getReader()`; no artificial delay is used. Errors become a safe SSE error event.

## 9. Security, containerization, and AWS
Locally, secrets live only in `.env`, which is excluded from Git (`.gitignore`) and from the Docker build context (`.dockerignore`) so the key never enters the image layers or version control. Validation, rate limiting, CORS and Helmet are active on every route. The Docker image listens at `0.0.0.0:$PORT`, exposes port 8080 and includes `/api/health` for container health checks. It is pushed to Amazon ECR and deployed via Amazon ECS Express Mode (the platform AWS recommends for new containerized workloads after closing AWS App Runner to new customers on April 30, 2026). `NVIDIA_API_KEY` is supplied to the running task as a plain environment variable set directly in the ECS task definition rather than a Secrets Manager reference — acceptable for a course-scale deployment, since the key is still never baked into the image or exposed to the browser, though a production system would reference it from Secrets Manager or SSM Parameter Store instead.

## 10. Challenges, solutions, testing and learnings

**Reasoning-model output leaking into the UI.** Switching the model from `meta/llama-3.2-3b-instruct` to the larger `nvidia/nemotron-3.5-lightning-30b-a3b` broke the app: the learning assistant streamed raw chain-of-thought ("Here's a thinking process: 1. Analyze user request...") straight into the answer box, and interview evaluation failed with "AI returned an invalid response." Nemotron is a reasoning model that, by default, spends part of its token budget on hidden thinking tokens which can appear directly in the visible output. The fix required two independent suppression signals sent with every NVIDIA request: a `chat_template_kwargs: { enable_thinking: false }` field and a `system` message reading "detailed thinking off." A first attempt at the former failed silently because it was wrapped in an `extra_body` key — a convention from the *Python* OpenAI SDK that the Node.js SDK does not recognise; the fix was spreading the field directly into the top-level request object.

**Truncated JSON from long answers.** A long, code-heavy candidate answer caused the evaluation JSON to be cut off mid-generation once it exceeded the token budget, producing a hard parse failure. This was fixed on three levels: the prompt was tightened to cap array lengths and word counts so responses stay predictably short; `max_tokens` was raised for headroom; and the `jsonrepair` library was added as a fallback parser that can recover a usable object (e.g. `score` and `verdict`) even from a string cut off mid-token, with any fields the model never got to generate backfilled with safe defaults instead of left `undefined`.

**A skipped question was scored anyway.** Skipping a question without answering still produced a plausible-looking score (e.g. 7/10) from the model, because the app asked the LLM to judge an answer that did not exist. The fix removed the model from that decision entirely: an empty or whitespace-only answer is now scored deterministically in application code (always 0, with a clear "Skipped" verdict) before any API call is made, which is both correct and faster.

**AWS App Runner closed to new customers mid-project.** AWS discontinued App Runner for new customers on 30 April 2026 and now recommends Amazon ECS Express Mode for new containerized deployments. The deployment plan and documentation were revised accordingly; ECS Express Mode still provisions a load balancer, HTTPS, auto scaling and a public URL automatically, so the change affected which console was used, not the container itself.

**Deployment picked up the wrong configuration.** After correcting the code, an update to the live ECS service still failed because two separate things were stale: `NVIDIA_BASE_URL` had been mistyped as `https://nvidia.com` (the marketing site, not the API host) instead of `https://integrate.api.nvidia.com/v1`, and — even after that was corrected — the ECS task definition's container image was still pinned to the image digest from the very first (broken) deployment, because pushing a new image to the same `:latest` tag in ECR does not automatically update an already-running service. Both the environment variables and the container image reference had to be corrected together before the redeploy picked up the fix.

**Testing approach.** Beyond production build and health-endpoint checks, fixes were verified with real requests rather than assumed: a mock OpenAI-compatible server was used to capture the exact JSON payload sent to NVIDIA and confirm the thinking-suppression fields were present; the same mock server was configured to return a model response truncated at the exact byte offset seen in production, to prove the `jsonrepair` recovery path actually works end-to-end through the real `evaluate()` function; and a server that always returns a hallucinated non-zero score was used to prove a skip is never even sent to the model. Full round-trip testing then continued through Docker build, ECR push, and the live ECS URL.

**Key learnings.** Reasoning-capable LLMs need explicit, provider-specific suppression of hidden reasoning tokens, and SDK conventions (like `extra_body`) do not transfer across languages without checking the target SDK's actual API. Any code path that turns model output into structured data needs a recovery strategy for partial/truncated responses, not just a try/catch. Decisions that must be deterministic and safety-critical to a grade or score (like "no answer was given") should never be delegated to a model's judgement. Finally, cloud platforms change: a deployment plan should be re-validated against current provider documentation rather than assumed stable for the whole project's duration.

## 11. Reflection, future improvements and live URL
The MVP is deliberately database-free so it works immediately; in-memory server sessions mean active sessions do not survive a server restart or task replacement, which is an accepted trade-off for a course project but a real limitation for production use. Both the server and client now retry transient AI-provider failures (network errors, 5xx responses) with backoff before surfacing an error to the user, which meaningfully improved reliability once real deployment traffic exposed occasional provider hiccups that a purely happy-path implementation had not accounted for. Future work: authentication, a persistent database (Postgres) so sessions survive restarts, saved historical reports server-side, voice-based interview mode, and richer analytics across attempts.
